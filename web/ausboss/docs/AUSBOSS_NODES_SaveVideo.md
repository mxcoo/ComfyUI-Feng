# 保存视频 🆎

把你的帧保存成输出文件夹里的视频文件，并在节点上播放结果。工作流被写进文件里，所以把 mp4 拖回 ComfyUI 就能恢复做出它的那张图。

节点上的播放器显示已保存视频的尺寸、fps、帧数和时长，竖长的视频整幅显示，并带一个 **LOOP** 控件。`gif` 和 `webp` 因为视频播放器放不了，只按图片显示，附带文件名。

播放器上方的 **Preview steps**（`step_preview`，默认关闭）会在片段生成过程中把它的第一帧一步步显示在播放器里，播放器上带一个 **STOP** 按钮。片段在头几步就看出不对时直接停掉，不必等到结尾；被停下的运行什么都不保存。保存好的视频会取代这些步骤画面。[分步预览](AUSBOSS_NODES_StepPreview.md) 页面有详细说明。

## 控件

- **frames**：要编码的 BHWC 帧批次。对子采样的格式，奇数尺寸会向里裁掉一个像素，变成它们要求的偶数尺寸。之所以可选，只是因为接上 `video` 时它会自带帧 —— 两者接一个就行。
- **FPS**（`fps`，初始为 `16`）：播放帧率。接上加载视频的 `fps` 输出可以保持源时间。它以整数帧为步进，但仍然是个浮点数，因为真实的广播帧率是 23.976、29.97 和 59.94 —— 这些可以手输，而整数输入会完全拒收加载视频的 `fps` 连线。
- **Prefix**（`filename_prefix`，初始为 `video`）：输出文件夹下的路径；子文件夹会自动创建。文件按 `<prefix>_00001_.<ext>` 递增命名。`%date:yyyy-MM-dd%` 这样的日期令牌可用，与 ComfyUI 自带的保存节点一致。输出文件夹之外的路径会被拒绝。
- **CRF**（`crf`）：质量 —— 越低越好、文件越大。h264 下 `19` 在视觉上无损。它在本地意味着什么取决于编码器；见下面的格式表。
- **Format**（`format`）：容器与编码器，见下文。
- **Ping-pong**（`pingpong`）：先正放再倒放，让它无缝循环。帧数和编码时间大致翻倍。折返处不重复首尾帧，所以循环不会卡一下。
- **Embed workflow**（`save_metadata`）：默认开启。关掉它，分享出去的文件里就不会嵌入你的提示词和节点图。若 ComfyUI 启动时带了 `--disable-metadata`，无论这里怎么设都不会嵌入。
- **audio**（可选）：要混进文件的音轨，例如加载视频的 `audio` 输出。
- **video**（可选）：核心的 `VIDEO` 句柄，例如加载视频的 `video` 输出。接上它会取代 `frames` 与 `audio` 输入 —— 改为编码该视频自带的帧和音轨。核心会在一个不可打断的步骤里解码它；见下文 *Cancel 触不到的那一段*。

## 帧率的优先级

接上的 `video` 带着它切帧时的帧率，这个帧率压过 `fps` 控件：用控件上过时的帧率重放那些帧，画面会相对旁边混入的音轨越走越偏。两者不一致时，ComfyUI 控制台会写一行说明实际使用的帧率。`video` 上没接线时，控件是唯一来源，控制台保持安静。

## 格式

| format | 是什么 | 音频 | crf 含义 |
| --- | --- | --- | --- |
| `mp4 h264` | 默认值；到处都能放 | AAC | `crf` |
| `mp4 h265` | 同质量下体积约一半，视支持而定 | AAC | `crf` |
| `mp4 h264 nvenc` | 在 NVIDIA GPU 上编码的 h264 —— 快得多，略大 | AAC | `cq` |
| `mp4 h265 nvenc` | 在 GPU 上的 h265 | AAC | `cq` |
| `webm vp9` | 用于网页分发 | Opus | `crf` |
| `webm av1` | 更新，比 vp9 更小 | Opus | `crf` |
| `mov prores` | ProRes HQ 剪辑母版；很大 | PCM | 忽略 |
| `mkv ffv1` | 位精确的无损；非常大 | FLAC | 忽略 |
| `gif` | 短的无声音循环，逐帧自适应调色板 | 无 | 忽略 |
| `webp` | 短的无声音循环，比 gif 小得多 | 无 | 质量 |

nvenc 格式需要 NVIDIA GPU 和可用的驱动，并会拒收大约 145x49 以下的帧。编码器起不来时，节点会说明这一点，并指出该改用哪个软件格式，而不是抛一段驱动栈报错。

`gif` 和 `webp` 没有流式编码器，所以每一帧都要先在内存里攒着，才写第一个字节 —— 这类格式只用于很短的片段。两者都不带元数据，所以它们没有内嵌工作流。

节点的界面跟着这张表走：所选格式忽略的控件会被隐藏，而不是留着看起来还有用。CRF 字段在 `mov prores`、`mkv ffv1` 和 `gif` 时会离开 **FPS · CRF** 这一行（上表里它们的对应行写的是 *忽略*），而 **Embed workflow** 行在 `gif` 和 `webp` 下会消失，因为它们带不了它。隐藏不等于移除：控件保留自己的位置和取值，保存的工作流照旧精确存取它，把格式切回来，它就带着原来的数字回来。

## 输出

每次运行一个文件。音频和视频落在同一个文件里 —— 没有单独的无音频副本。内嵌的工作流在 mp4、mov、webm 和 mkv 中都能保住；matroska 会把标签名转成大写，这只对直接读这些标签的工具可见。

节点还有一个 **file_path** 输出：它刚写出的文件的绝对路径，可以接到需要文件本身的下游节点。不接也什么都不会变 —— 节点照样保存。

## 运行过程中

编码在 ComfyUI 的执行线程之外进行，所以写长批次时服务器仍在响应。节点的进度条逐帧填充，**Cancel** 会在一帧之内停掉编码，而不是等到批次结束。混入的音频在画面之后编码，所以进度条会重新开始，转而数那条音轨的音频帧；**Cancel** 在其中一帧之内停下。

### Cancel 触不到的那一段

接上 `video` 会增加一个本节点控制不了的步骤。ComfyUI 核心会在第一帧进到本包之前把整个文件读完 —— 每一帧都解码成 float32 —— 而做这件事的核心调用 `VideoInput.get_components()` 不接受进度或中断参数，没地方把中断传进去。所以这一段没有进度，也不会因 **Cancel** 而停下：取消会立刻登记（解码跑在执行线程之外，服务器仍在响应），并在编码的第一帧、控制权回到这里时生效。

这一段持续多久取决于像素数量，而不是文件大小。在一台桌面上实测：832x480、16 fps 的十秒片段约 0.6 s 返回；1080p、30 fps 的十秒片段用了约 7 s，并在内存里压着 7.5 GB 的帧。要避免的是几分钟的高分辨率素材 —— 内存会先于等待耗尽。改成接加载视频的 `frames` 输出而不是 `video`，整个运行就都可中断、都有进度，因为那次解码是本包自己的循环。
